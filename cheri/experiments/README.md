# Experiment: the two leaves, compiled purecap

This directory holds four experiments. This file is the first. The
second, the MVP monitor run unchanged on a CHERI hart with the hypervisor
extension (2026-11-04), is [`monitor-run.md`](monitor-run.md). The third,
CHERI-enabled guests under the monitor (2026-11-04), a bare-metal test
guest and then a minimal CHERI Linux guest, is
[`cheri-guest.md`](cheri-guest.md). The fourth, a CHERI-enabled version of
Beryllium's MVP judged by Beryllium's own checks (2026-11-05), is
[`be-cheri-poc.md`](be-cheri-poc.md).

## Result (2026-11-03; scoped after review)

At Beryllium commit `6fbcc3d1`, the two source files that hold M8's leaves,
`mvp/src/mvp-sbi.c` (with `be_mvp_denial_decide`) and `mvp/src/mvp-ring.c`,
compile unchanged as purecap CHERI-RISC-V v0.9.3 code with the CHERI
Alliance LLVM (`codasip-cheri-riscv-20`, `65b9e7ef`). They were compiled
under Beryllium's recorded flags, with only `-march`/`-mabi` changed, and
produced no warnings or errors, including with the 11 CHERI warning groups
that compiler accepts (sub-object bounds not enabled). A hybrid compile is
equally clean; for this code it emits no capability instructions.
Beryllium's host tests `deny-test` and `ring-test`, built unchanged as
static purecap Linux programs, pass in user mode on CHERI Linux
(`codasip-cheri-riscv-7.1`) under QEMU `codasip-latest`, CPU model
`codasip-x730-lux`, which has no hypervisor extension. Both reach
Beryllium's pinned counts (38 scenarios and 2,933 assertions; 160 and
409,415) and print the same three lines as the x86-64 host build.

That is a result about two source files and two tests, for v0.9.3 under
emulation with default bounds. It says nothing about RVY (v0.9.10), the
hypervisor extension, the leaves' callers, the trap vector, start-up code,
the board, or any hardware, and it is not a proof of anything. The
evidence is `diagnostics.txt` (eight compiles, each object's flags, and a
positive control), `results.txt` (the test builds, the run, and the
verdicts), and `leaves.sha256` (the inputs); the pins are in
`../tools/pins.txt`. An AI review of this wording is
`../docs/reviews/2026-11-03-dossier-review.md`.

## Method

The route is Codasip's v0.9.3 stack under Codasip's QEMU branch, the
responsible human's choice of 2026-11-03.

1. `extract-inputs.sh` reads the leaves, their headers, and the host
   tests from Beryllium at `6fbcc3d1` by `git show`, plus `mvp-gstage.c`,
   which Beryllium's `mvp/Makefile` links into `deny-test`. The two units
   and their 11 headers must equal Beryllium's frozen record,
   `mvp/verify/target-digests.txt`. That record was added after the target
   (at `58ee7fd8`), so it is read there. Two of its headers, `r3.h` and
   `manifest.h`, are rewrites generated by the `port` target of
   Beryllium's `mvp/Makefile`, so they come from that step's output.
   `leaves.sha256` records all 16 files.
2. `compile-leaves.sh` compiles each leaf with Beryllium's recorded
   `compile_flags`, changing only `-march` (adding `zcherihybrid` and
   `zcherilevels`) and `-mabi` (`l64pc128` purecap, `lp64` hybrid). It
   compiles each mode twice: as Beryllium builds (`-Werror`), and with
   `-Werror` off and the 11 CHERI warning groups the compiler accepts. It
   records each object's ELF flags and how many of its instructions name a
   capability register: the purecap objects are marked `cheriabi,
   capability mode`, and the hybrid objects have none. A two-line positive
   control that casts between integers and pointers draws
   `-Wcheri-capability-misuse` and `-Wcapability-to-integer-cast` under
   the same groups.
3. `run-tests.sh` builds both tests with Beryllium's recorded
   `host_test_flags` and cheribuild's purecap userland flags, puts them in
   a BusyBox initramfs, and boots the pinned CHERI Linux kernel under the
   pinned QEMU. It checks each test as Beryllium's `host-test` does:
   exactly three lines, `PASS`, the pinned counts, and exit status 0. It
   also compares the output with a build for the x86-64 host.

## Reproduce

From this repository's root, with a Beryllium checkout that contains
`6fbcc3d1` and `58ee7fd8` and has run its `port` step:

1. `experiments/fetch-stack.sh` fetches each pinned commit into
   `toolchains/` and prints its `git archive` SHA-256.
2. `experiments/build-stack.sh` builds the stack with cheribuild, then
   QEMU with `build-qemu.sh`; it takes about 25 minutes on 28 cores.
3. `experiments/extract-inputs.sh BERYLLIUM_CHECKOUT`
4. `experiments/compile-leaves.sh BERYLLIUM_CHECKOUT` writes
   `diagnostics.txt`.
5. `experiments/run-tests.sh BERYLLIUM_CHECKOUT` writes `results.txt`; set
   `CPU=` to choose another QEMU CPU model.
6. `experiments/fw-jump-fault.sh` writes `fw-jump-fault.txt` (see Notes).

No root access is needed. Nothing fetched or built is committed.

## Notes

- Each purecap test link prints two `ld.lld` warnings. Both come from the
  toolchain's startup objects (`crt1.o`, `crtbeginT.o`), none from
  Beryllium's sources.
- This OpenSBI's `fw_jump` hands the kernel a device tree at
  `0x82200000`, inside the 62 MB purecap kernel image (physical
  `0x80200000` to `0x84909b61`). With it, the kernel's read-only table
  `riscv_a_exts` reads `0x02000000` instead of its linked `0x61`, and the
  kernel takes a CHERI fault in `riscv_isa_set_ext`: the bad value sends
  an atomic bit-set 4 MiB past a 16-byte bitmap, and the capability for
  that address has lost its tag, so the access traps (exception 28)
  instead of writing past the bitmap. `fw-jump-fault.txt` records the
  console lines, the table's two values, and the instruction trace. The
  failure was the same with the generic and `codasip-x730-lux` CPU models.
  `fw_dynamic` from the same build keeps QEMU's device tree at the top of
  RAM, and the run uses it.
- QEMU 8.1's `configure` needs Python's `distlib`. `build-qemu.sh` uses the
  pinned wheel in an isolated venv under `toolchains/`.
- The tests also pass with cheribuild's generic model
  (`CPU="rv64,cheri_pte=on,cheri_levels=2"`); `results.txt` records the
  `codasip-x730-lux` run.
- Not exercised: sub-object bounds (`-Xclang -cheri-bounds=subobject-safe`),
  running the tests in hybrid mode, capability faults, fault injection,
  the leaves' callers (`mvp-hartmain.c`, `mvp-runtime.c`), RVY, and the
  hypervisor extension.
